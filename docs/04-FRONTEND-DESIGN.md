# InvoiceReady — Frontend & Hosting Technical Design
Version 1.1 · Scope: V1 (Compliance Navigator) · Companion to `02-TECHNICAL-DESIGN.md`

> **v1.1 (14 Sep 2026)** — the landing screen moved from a single centred column to a **two-column split with a live assessment preview** (see §3.1–§3.2), after design review. This is not a cosmetic change: the assessment components must now render from partial data, which affects §4.5, §5 and §9. The stack, hosting and design tokens are unchanged.

---

## 0. What this document changes

`02-TECHNICAL-DESIGN.md` specified *"Server-rendered Jinja2 templates + vanilla JS"* and Railway for deployment. Two things have changed since:

1. **The UI is now a portfolio artifact, not just a surface.** The first thing a hiring manager does is click the link. A Jinja page with hand-rolled CSS reads as "backend engineer who shipped a form"; a polished, responsive, dark-mode-capable app reads as "engineer who ships products." Same backend, different first impression.
2. **The hosting constraint is now explicit: €0/month, always-on link.** Railway has no meaningful free tier, and a portfolio link that 404s or takes 60 seconds is worse than no link.

**Superseded decisions:**

| `02-TECHNICAL-DESIGN.md` said | Now |
|---|---|
| Frontend: Jinja2 + vanilla JS | React SPA (Vite + TypeScript + Tailwind + shadcn/ui), static build |
| `app/templates/` in the FastAPI app | Removed. FastAPI becomes a pure JSON API. |
| Deployment: Railway | Cloudflare Pages (frontend) + Render free (API) + Neon free (Postgres/pgvector) |
| Embeddings: local `sentence-transformers` | `fastembed` (ONNX) — see §9.4, the 512 MB RAM constraint is real |

Everything else in `02` stands: the hybrid retrieval design, the rules-engine-not-LLM decision, the grounding and refusal contract, the data model, the API contracts.

## 1. Frontend principles

**This is a compliance product. The UI's job is to earn trust, not to impress.** Restraint *is* the modern look here — generous whitespace, one accent colour, real typographic hierarchy, no gradients-on-everything. Stripe and Linear, not a crypto landing page.

Four principles, in priority order:

1. **Every claim shows its receipt.** Source link and "last reviewed" date are first-class UI components, not footnotes. This is the single most important visual difference between this product and a ChatGPT wrapper — make it visible.
2. **A refusal must look like a feature, not a failure.** When the system says "I don't know, here's the official source," that state gets a designed card — not a red error toast. Recruiters who read the `/how-it-works` page will understand why.
3. **The page never depends on the backend being awake.** See §6, demo mode.
4. **Nothing on screen that the API can't back.** No fake charts, no placeholder logos, no "trusted by" strip. One invented testimonial destroys the credibility the sources bought you.

## 2. Stack

| Concern | Choice | Rationale |
|---|---|---|
| Build tool | **Vite** | Fast, zero-config, static output. No SSR server to host. |
| Framework | **React 19 + TypeScript** | Most transferable; Claude Code writes it well; strict mode catches contract drift. |
| Styling | **Tailwind CSS v4** | Design tokens as CSS variables → dark mode for free. No CSS file to maintain. |
| Components | **shadcn/ui** | Copy-in components (Radix under the hood), so you own the code and it lives in your repo — accessible by default, and no dependency that can restyle your app in a minor version. |
| Icons | **lucide-react** | Matches shadcn, consistent stroke weight. |
| Data fetching | **TanStack Query** | Caching, retries with backoff, and loading/error state machines — exactly what a cold-starting free-tier API needs. |
| Forms | **react-hook-form + zod** | One zod schema validates the intake form *and* types the request body. |
| Routing | **React Router** | Three routes; don't reach for more. |
| API types | **`openapi-typescript`** against FastAPI's `/openapi.json` | Backend Pydantic models are the single source of truth. Contract drift becomes a TypeScript error, not a production bug. Generated into `src/api/schema.d.ts`, committed, regenerated by a script. |
| Motion | **CSS transitions**; `framer-motion` only if a specific interaction needs it | 150–200 ms ease-out. Restraint. |
| Charts | **None in V1** | There is no data worth charting yet. A timeline is a list, not a chart. |
| Testing | **Vitest + React Testing Library**, plus **Playwright** for one happy path | Test the refusal state and the demo/live toggle; skip snapshot tests. |
| Lint/format | **ESLint + Prettier** (or Biome) | Mirror `ruff`'s role on the Python side. |

**Why not Next.js:** you would be adding SSR, a Node runtime, and Vercel gravity to solve a problem you don't have yet. V1 has no SEO surface — the country landing pages from the GTM plan are a V2 content project. A static SPA deploys anywhere, costs nothing, and can be migrated to Next.js later if the SEO play becomes real. Say exactly this if you're asked in an interview.

**Why not Jinja + HTMX:** defensible, and half the setup — but the whole page then dies with the backend, which is fatal under §1.3, and the ceiling on visual polish is lower.

```
/result              Assessment output (+ inline grounded Q&A)
```

**Why the split.** The single-column wizard asked for three answers before showing anything. The right panel shows the assessment being assembled from the first click — and puts "every claim cites an official source", the product's actual differentiator, on screen before the user has committed anything. It costs one extra component and buys the entire value proposition above the fold.

Three steps, unchanged in substance: **country** → **VAT status + size** (employees, turnover band) → **who you invoice** (B2B / B2C / B2G, multi-select). One question per step in the left column, large targets, keyboard-navigable, back always available, progress visible. Each step maps directly to the `POST /api/assess` body in `02-TECHNICAL-DESIGN.md` §5.

Turnover is a **band selector**, not a number input — people don't know their exact figure, and the rules engine only needs the threshold comparison. Bands must be chosen so every band sits unambiguously on one side of every threshold in the `rules` table.

**Brand mark:** a ring of twelve dots (the EU stars, abstracted so they stay legible at 19px), plus the wordmark. The same twelve-star ring appears as a large, ~10%-opacity motif bleeding off the top-right of the preview panel. Drawn as inline SVG in the accent colour — never an emoji flag, which renders differently on every platform and can't be recoloured.

### 3.2 The assessment preview (right panel)

This is the component with real engineering consequences, so it gets its own contract.

**The preview and the result page render the same data through the same components.** The only difference is completeness. Therefore:

- Every assessment component (`DeadlineStrip`, `ObligationCard`, `NextSteps`, `SourceList`) accepts `data | undefined` per field and renders a **skeleton** for `undefined` — sized to the real content so nothing jumps when it resolves.
- The preview never calls `/api/assess`. It renders locally from intake state plus `/api/countries` metadata (country name, coverage status, `last_reviewed`). A partial profile has no assessment to fetch, and firing a request per keystroke would burn the Anthropic budget for nothing.
- Only after all three steps are answered does submitting call `/api/assess` and route to `/result`.
- The preview is **honest about being incomplete**: the `YOUR ASSESSMENT · BUILDING` label and "Answer two more questions to complete it" are load-bearing, not decoration. A half-built assessment must never read as a finished one — in a compliance product that is a correctness issue, not a UX nicety.

**Mobile (< 900px):** the grid collapses to one column and the preview panel moves **below** the intake, keeping the form above the fold. The panel's gradient and star motif are dropped at that width rather than being shrunk. Do not make the preview a sticky bottom sheet in V1 — it steals vertical space from a form that is the whole point of the screen.

### 3.3 `/result` — the assessment

Vertical composition, in order:

1. **Verdict card** — the answer in one sentence, at h2 size: *"Yes — from 1 September 2026 you must be able to receive structured e-invoices."* Status colour on the left border only (green in scope / amber upcoming / slate not applicable). Never a full-bleed coloured panel.
2. **Deadline strip** — the date, large, tabular numerals, plus a live countdown (`in 11 months`). The single most-screenshotted element in the product; make it good.
3. **Obligation cards** — one per row in `obligations[]`. Each carries: `rule_type` badge (issue / receive / report), `applies_from`, format + network as monospace chips (`Peppol BIS 3.0`, `PDP`), the LLM's plain-language `explanation`, and a `SourceBadge` with `source_url` + `source_reviewed_at`.
4. **Next steps** — `next_steps[]` as a numbered checklist with local (`localStorage`) check state. Free, and it makes the page feel like a tool rather than a report.
5. **Ask a follow-up** — inline `POST /api/ask` panel (§3.3).
6. **Sources** — every URL used on the page, collected, each with its review date.
7. **Disclaimer** — persistent, not dismissible.

### 3.4 Grounded Q&A panel

Three designed states, one component:

- **Answered** — prose with inline citation chips `[1]` that scroll-link to the source list. Citations render from `citations[]`; a claim with no citation should be visually impossible to produce.
- **Refused** (`refused: true`) — a neutral, *confident* card: "This isn't in the knowledge base for France. Here's the official source →". Muted background, info icon, no red, no apology. This is a deliberate design choice and it belongs in your README.
- **Out of scope / streaming** — skeleton lines matching the final text layout, never a centred spinner.

Three suggested starter questions per country, pulled from the eval set, so the user doesn't face an empty box.

### 3.5 `/how-it-works` — the portfolio page

This page exists for hiring managers, and it costs you almost nothing because the content is already written in `01` and `02`.

- The architecture diagram (rules engine vs. LLM boundary), as inline SVG
- **"Why the LLM never decides your deadline"** — three paragraphs on the deterministic rules table
- Live evaluation results: *N questions, X% correct, all Y refusal cases passing* — read from a committed `eval_results.json` produced by `scripts/run_eval.py`. Real numbers, dated.
- Trade-offs you chose and rejected (no framework, hybrid retrieval, 3 countries deep not 12 shallow)
- Links: GitHub repo, demo video

Most portfolio projects don't have this page. It is the cheapest differentiator available to you.

## 4. Design system

Defined once as CSS variables in `src/index.css`; Tailwind v4 consumes them. Light and dark from day one — the dark variant is one block of overrides, and reviewers on dark-mode browsers notice.

### 4.1 Colour

```css
:root {
  --background: 0 0% 100%;
  --foreground: 222 22% 11%;      /* near-black, never pure #000 */
  --muted: 220 14% 96%;           /* section backgrounds */
  --muted-foreground: 220 9% 46%;
  --border: 220 13% 91%;
  --primary: 231 48% 48%;         /* indigo — one accent, used sparingly */
  --primary-foreground: 0 0% 100%;
  --success: 142 55% 36%;         /* in scope, ready */
  --warning: 38 92% 42%;          /* deadline approaching */
  --danger:  0 72% 45%;           /* penalties only — never for refusals */
  --radius: 0.75rem;
}
```

Rules: one accent colour, used for primary actions and nothing else. Status colours appear only as left borders, small badges, and icons — never as large filled areas. Red is reserved for penalty information; a refusal is **not** an error.

### 4.2 Typography

- UI + body: **Inter** (or system stack) — `-webkit-font-smoothing: antialiased`
- Numerals: `font-variant-numeric: tabular-nums` on every date, threshold, and countdown
- Code-ish values (`EN 16931`, `Peppol BIS 3.0`, `UBL 2.1`): monospace chips — these strings are intimidating jargon to the user, and treating them as artifacts rather than prose is honest
- Scale: 48 / 30 / 20 / 16 / 14 / 12. Body 16px minimum, `max-w-[68ch]` on prose, `leading-relaxed`

### 4.3 Surfaces and motion

One shadow level (`shadow-sm`), borders do the structural work. `--radius` 12px everywhere. Content column `max-w-3xl`, centred, `px-6`. Transitions 150 ms ease-out on hover/focus; content entering the page fades and rises 4px over 200 ms; obligation cards stagger 40 ms. Everything wrapped in `@media (prefers-reduced-motion: reduce)`.

### 4.4 Accessibility (non-negotiable, and cheap with shadcn)

Visible focus rings, 4.5:1 contrast minimum, the wizard fully keyboard-operable, `aria-live="polite"` on the answer region, real `<label>`s, `<h1>`→`<h2>` order intact. Target: Lighthouse accessibility ≥ 95. Put the score in the README.

### 4.5 Trust components (build these first)

`<SourceBadge url reviewedAt />` · `<LastReviewed date />` (amber if > 90 days old) · `<RefusalCard />` · `<DisclaimerBar />` · `<CoverageIndicator />` · `<AssessmentPreview profile />` (§3.2) · `<Skeleton w h />`. Everything else is composition.

`<Skeleton>` is a trust component, not a styling helper: it is what stops a partially-known assessment from looking complete. Every assessment field renders either real data with its source, or a skeleton — never a plausible-looking placeholder value.

```
│   │   └── index.ts               # picks implementation from env/toggle
│   ├── components/
│   │   ├── ui/                    # shadcn primitives (owned, committed)
│   │   └── trust/                 # SourceBadge, RefusalCard, DisclaimerBar…
│   ├── features/
│   │   ├── intake/                # wizard steps, zod schema
│   │   │   └── useIntakeState.ts  # SHARED source of truth (§5.1)
│   │   ├── assessment/            # verdict, deadline, obligations —
│   │   │   │                      #   every component partial-data capable (§3.2)
│   │   │   └── AssessmentPreview.tsx
│   │   └── ask/                   # Q&A panel + citations
│   ├── pages/                     # Landing, Result, HowItWorks
│   ├── lib/                       # dates, url-state, cn()
│   └── demo/fixtures/*.json       # snapshotted real API responses
├── public/
└── tests/
```

Monorepo-style single repo: `frontend/` beside `app/`. One repo, one commit history, one README — better for a portfolio than two repos a reviewer has to stitch together.

### 5.1 Intake state is lifted, not local

The split layout means two columns read the same answers, so intake state cannot live inside the wizard. One hook owns it:

```ts
// features/intake/useIntakeState.ts
type IntakeState = {
  country?: CountryCode;
  vatRegistered?: boolean;
  employeeBand?: EmployeeBand;
  turnoverBand?: TurnoverBand;
  invoicesTo?: Counterparty[];
};
```

- Held at the `/` route component, passed down to the wizard (writes) and `AssessmentPreview` (reads). No context provider, no store library — this is one object and two consumers.
- Mirrored into the URL query string on every change, so a half-finished intake survives a refresh and the completed profile is the same encoding `/result` already reads.
- `zod` validates it per step; the completed object is exactly the `POST /api/assess` body, so there is no mapping layer to keep in sync.

**Contract discipline:** `npm run gen:api` runs `openapi-typescript http://localhost:8000/openapi.json -o src/api/schema.d.ts`. CI regenerates and fails the build on a diff — the frontend cannot silently drift from the backend's Pydantic models.

## 6. Demo mode (the reason the link always works)

Free backends sleep. A visitor must never see a spinner that outlasts their patience.

**Design:** all data access goes through one interface, with two implementations.

```ts
interface DataSource {
  countries(): Promise<Country[]>;
  assess(input: AssessRequest): Promise<AssessResponse>;
  ask(input: AskRequest): Promise<AskResponse>;
}
```

`countries()` is what the preview panel (§3.2) reads, so the landing screen is fully alive on fixtures alone — a visitor sees the product working before any backend is touched.

- `DemoDataSource` — resolves from `src/demo/fixtures/*.json` with a simulated 400–700 ms delay so it *feels* like a real request.
- `HttpDataSource` — real `fetch` against `VITE_API_BASE_URL`, via TanStack Query.

Default on the deployed site: **demo**, with a persistent, honest header pill:

> **Demo data** — instant, no backend needed. **[Run it live →]** (*wakes a free-tier server, ~40 s*)

Flipping to live persists in `localStorage` and a `?live=1` param, so you can send a recruiter the live link directly.

**Fixtures must not be hand-written.** `scripts/snapshot_fixtures.py` calls the local API for every country × representative profile and writes the JSON verbatim into `frontend/src/demo/fixtures/`. This keeps demo output identical to real output and makes drift impossible to fake. Include at least one **refusal** fixture and one **not-in-scope** fixture — the interesting states.

**Cold-start UX when live:** on the first live call, show a wake card with a determinate ~45 s progress bar and honest copy ("The API runs on a free tier and sleeps when idle — this is a cost decision, not a bug"). TanStack Query retries 3× with exponential backoff; on final failure, fall back to the demo fixture and say so. Optionally fire a `GET /health` on toggle so warm-up starts before the user submits.

That honest copy is itself a signal: it says you understand infrastructure cost trade-offs and chose deliberately.

## 7. Backend changes required

Small, but they are prerequisites:

1. **Drop `app/templates/`** and the HTML routes. FastAPI serves JSON only.
2. **CORS** — `CORSMiddleware` with an explicit allowlist from env (`ALLOWED_ORIGINS`): the Pages production domain, `*.pages.dev` previews, `http://localhost:5173`. No wildcard.
3. **`GET /health`** — already planned; must be cheap and must not touch the LLM. It is also the warm-up ping.
4. **Rate limiting** on `/api/ask` and `/api/assess` (`slowapi`, per-IP, e.g. 10/min, 100/day). Your Anthropic budget is exposed to the public internet the moment you deploy — this is the guard.
5. **`GET /api/countries`** — returns coverage + `last_reviewed` per country, so the frontend never hardcodes what the knowledge base contains.
6. **Response caching** by profile hash (already in `02` §7) — matters more now, since a shared portfolio link means the same handful of profiles get requested repeatedly.

## 8. Hosting architecture (€0/month)

```
        Visitor
           │
           ▼
  ┌─────────────────────┐
  │  Cloudflare Pages   │   static React build · global CDN · always on
  │  invoiceready.pages.dev │   free TLS · preview deploy per PR
  └─────────┬───────────┘
            │  HTTPS + CORS  (only when "live" is toggled)
            ▼
  ┌─────────────────────┐
  │   Render — free     │   FastAPI in Docker · 512 MB RAM
  │   web service       │   sleeps after 15 min idle, ~60 s cold start
  └─────────┬───────────┘   750 instance-hours/month per workspace
            │
            ▼
  ┌─────────────────────┐
  │   Neon — free       │   Postgres 17 + pgvector · 0.5 GB storage
  │   serverless PG     │   scale-to-zero after 5 min (~sub-second wake)
  └─────────────────────┘   100 CU-hours/month · no 30-day expiry
```

### 8.1 Why each choice

**Frontend → Cloudflare Pages.** Free tier includes unlimited bandwidth, free custom domains and TLS, 500 builds/month, preview deployments per branch — and, unlike Vercel's Hobby plan, it does not restrict you to non-commercial use. That clause matters: your business plan has a paid tier in it, and Vercel Hobby is explicitly personal/non-commercial. Cloudflare Pages avoids having to migrate the day the project stops being a portfolio piece. (Vercel Hobby and Netlify Free are fine fallbacks if you hit a Cloudflare limitation; the static build is portable either way.)

**API → Render free web service.** 750 free instance-hours per workspace per month, Docker-native, deploys from GitHub. It sleeps after 15 minutes idle with a ~1 minute cold start, and the filesystem is ephemeral — both acceptable, because demo mode absorbs the cold start and nothing is written to disk. Alternatives considered: Railway (no real free tier — credit trial), Fly.io (free allowance withdrawn), Hugging Face Spaces (free CPU tier has been restricted and is Gradio/Docker-shaped, wrong signal for a FastAPI product).

**Database → Neon, not Render Postgres.** This is the trap to avoid: **Render's free Postgres expires 30 days after creation** and is deleted after a grace period. A portfolio database that self-destructs in a month is a broken link with extra steps. Neon's free plan gives 0.5 GB per project with no such expiry, scale-to-zero after 5 minutes idle, ~100 CU-hours/month, and `pgvector` is supported — which is exactly what `02`'s schema requires. 0.5 GB is generous for three countries of rules and 384-dimension chunk embeddings; expect single-digit MB.

**Domain.** `*.pages.dev` is free and fine. If you want `invoiceready.eu`, that's an annual registration (~€10–15/yr), not a monthly hosting cost — worth it once the project is on your CV, not before.

**The only variable cost is the Anthropic API**, and it is zero while the site is in demo mode. Set a hard spend cap in the console before the first deploy, and keep the rate limits from §7.4.

### 8.2 Free-tier risk register

| Risk | Impact | Mitigation |
|---|---|---|
| Render's free tier changes or is withdrawn | API link dies | Demo mode keeps the site fully functional; Dockerfile makes the API portable to any host in an afternoon |
| Neon free storage (0.5 GB) exceeded | Writes fail | 3 countries ≈ a few MB. Monitor before adding countries in V2. |
| Cold start deters a live visitor | Bad impression | Demo default + honest wake UI + optional `/health` prewarm |
| Public endpoint burns Anthropic credit | Budget gone | Per-IP rate limits, profile-hash cache, hard console spend cap |
| Free-tier limits shift again | Doc goes stale | Facts here were checked 14 Sep 2026 — re-verify before deploy day |

### 8.3 Environment configuration

| Where | Variable | Value |
|---|---|---|
| Cloudflare Pages | `VITE_API_BASE_URL` | `https://invoiceready-api.onrender.com` |
| Cloudflare Pages | `VITE_DEMO_MODE` | `true` |
| Render | `ANTHROPIC_API_KEY` | secret |
| Render | `DATABASE_URL` | Neon pooled connection string |
| Render | `ALLOWED_ORIGINS` | Pages prod domain + `*.pages.dev` + localhost |
| Render | `ENV` | `production` |

Build command `npm run build`, output `dist/`, root `frontend/`.

### 8.4 The 512 MB constraint — resolve this before deploying

`02` specified local `sentence-transformers` embeddings. **`torch` + `sentence-transformers` will not fit in Render's 512 MB free instance** (the image alone is >2 GB, and resident memory exceeds the cap). Two ways out:

- **Recommended: `fastembed`** — ONNX runtime, `BAAI/bge-small-en-v1.5` or `all-MiniLM-L6-v2`, ~100–200 MB resident, **384 dimensions**, which matches `VECTOR(384)` in the existing schema with no migration. Runs on CPU, no per-call cost.
- Alternative: a hosted embedding API (Voyage, Cohere) — smaller container, but adds a network hop, a second key, and a second thing that can rate-limit you.

Either way, **chunk embeddings are computed offline** by `scripts/ingest.py` on your laptop and written to Neon. The deployed service only ever embeds a single short user query, which is well within budget.

### 8.5 CI/CD

- **Cloudflare Pages**: connects to the GitHub repo, builds on push to `main`, preview URL per pull request. No config needed beyond build settings.
- **Render**: auto-deploy from `main`, Dockerfile build, Alembic migrations in the start command.
- **GitHub Actions** (`.github/workflows/ci.yml`): `ruff` + `pytest` for the backend; `tsc --noEmit` + `vitest` + `npm run build` for the frontend; regenerate `schema.d.ts` and fail on diff. A green badge in the README is free credibility.

## 9. Build order

Roughly one week on top of the `01` timeline, and it slots into week 4 ("Web UI").

| Order | Work | Why here |
|---|---|---|
| 1 | Backend: CORS, `/health`, `/api/countries`, rate limits | Frontend can't start without a stable contract |
| 2 | Scaffold Vite + TS + Tailwind + shadcn; tokens from §4.1; dark mode | Design system before screens, or you retrofit forever |
| 3 | Generate `schema.d.ts`; build `DataSource` + demo fixtures | Build the whole UI against fixtures — no backend dependency, no token spend |
| 4 | Trust components (§4.5), incl. `Skeleton` | They appear on every screen |
| 5 | `useIntakeState` + wizard + zod + URL state (§5.1) | The preview can't be built before the state it reads |
